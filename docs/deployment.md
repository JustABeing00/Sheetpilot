# SheetPilot deployment guide

Production topology:

```
Browser
  │  https://sheetpilot.com            (Cloudflare Worker: static assets + API proxy)
  ▼
Cloudflare Worker  ──/api/*,/healthz,/readyz──▶  Render web service (Fastify API)
  │  serves apps/web/dist (SPA)                          │
  ▼                                                      ▼
static assets                                    Render Postgres + persistent disk
```

The Worker serves the SPA and proxies API calls to Render, injecting the `x-api-key` header
server-side. The API key never reaches the browser, and the app stays same-origin (no CORS).

## Repository artifacts

| File | Purpose |
| --- | --- |
| `Dockerfile` | Multi-stage build for the API (build → pruned runtime), used by Render. |
| `.dockerignore` | Keeps the image small (no tests, docs, samples, local data). |
| `render.yaml` | Render Blueprint: web service + Postgres + persistent disk + env vars. |
| `apps/web/wrangler.jsonc` | Cloudflare Worker config (static assets + SPA fallback + proxy). |
| `apps/web/worker/index.js` | Worker entry: serves assets, proxies the API, injects `x-api-key`. |
| `apps/web/public/_headers` | Security headers (CSP, HSTS via Cloudflare, cache policy). |
| `apps/web/public/_redirects` | `/favicon.ico` → `/favicon.svg`. |
| `.nvmrc`, `Dockerfile` | Pin Node 22. |

## Prerequisites

- A Render account and a Cloudflare account.
- `wrangler` (installed as a dev dependency of `apps/web`) and `wrangler login`.
- The repo pushed to GitHub (Render auto-deploys from it).

## Step 1 — Deploy the API on Render

1. Render Dashboard → **New → Blueprint**, connect the repository. Render reads `render.yaml` and
   creates `sheetpilot-api` (Docker web service), `sheetpilot-db` (Postgres 16) and a 1 GB disk at
   `/data`.
2. Render generates `API_KEY`. Open the service → **Environment** and copy its value.
3. Wait for the first deploy. The service:
   - builds the Docker image (`npm ci && npm run build`, then `npm prune --omit=dev`),
   - starts with `NODE_ENV=production`, `REPOSITORY_DRIVER=postgres`, `DB_AUTO_MIGRATE=true`,
   - applies migrations at startup (single instance) and listens on the platform `PORT` at `0.0.0.0`.
4. Verify:
   - `https://<service>.onrender.com/healthz` → `{"status":"ok",...}`
   - `https://<service>.onrender.com/readyz` → `{"status":"ready",...}` (fails with 503 if Postgres is
     unreachable).
5. Note the service URL — it becomes `API_ORIGIN` for the Worker.

Keep the service at **one instance**. Runs execute in-process; a second replica would mark the first
replica's in-flight runs as failed on boot. Do not enable autoscaling until a durable job queue exists.

### Manual setup (without the Blueprint)

- Web service, runtime **Docker**, Dockerfile path `./Dockerfile`, health check `/healthz`.
- Add a persistent disk mounted at `/data`; set `STORAGE_LOCAL_DIR=/data/storage`.
- Environment: `NODE_ENV=production`, `API_HOST=0.0.0.0`, `TRUST_PROXY=true`,
  `REPOSITORY_DRIVER=postgres`, `DATABASE_URL=<internal connection string>`, `API_KEY=<secret>`,
  `DB_AUTO_MIGRATE=true`, `DB_MIGRATIONS_DIR=/app/packages/db/drizzle` (the Dockerfile sets this).
- Create a Postgres 16 instance and link `DATABASE_URL`.

## Step 2 — Deploy the frontend as a Cloudflare Worker

1. Set the API origin in `apps/web/wrangler.jsonc`:
   ```jsonc
   "vars": { "API_ORIGIN": "https://<service>.onrender.com" }
   ```
2. Build and deploy:
   ```bash
   cd apps/web
   npm run build                 # vite build -> apps/web/dist (+ public assets)
   npx wrangler login
   npx wrangler secret put API_KEY   # paste the value generated by Render
   npm run deploy                    # wrangler deploy
   ```
   (`wrangler deploy` reads `wrangler.jsonc`, uploads `dist/`, and registers the Worker + `ASSETS`
   binding. `not_found_handling: single-page-application` gives client-side routes like `/dashboard`
   the right fallback.)
3. Custom domain: Worker → **Settings → Domains & Routes → Add custom domain** (`sheetpilot.com`).
   Cloudflare provisions TLS automatically.
4. Verify:
   - `https://sheetpilot.com/` loads the landing page.
   - `https://sheetpilot.com/healthz` and `/readyz` reach Render through the proxy.
   - Downloading a report from a run works (the Worker adds the key).
5. Optional hardening: put **Cloudflare Access** in front of the Worker to require an email/SSO login
   for the pilot. The Worker's injected `API_KEY` remains defense in depth.

### Local Worker development

```bash
cd apps/web
npm run build
npx wrangler dev --var API_ORIGIN:http://127.0.0.1:4000
```
For UI work, `npm run dev` (Vite + proxy) is still the fastest loop.

## Migrations

- **Default:** `DB_AUTO_MIGRATE=true` applies pending migrations at API startup (safe with one
  instance). Recommended for this topology.
- **Explicit (preferred for multi-step deploys):** set `DB_AUTO_MIGRATE=false` and add a Render
  **Pre-Deploy Command**: `node apps/api/dist/index.js --migrate`. This runs the bundled migrator with
  no TypeScript toolchain and exits.
- **Local/CI:** `npm run db:migrate` (runs the source script with `tsx`).

The migrations folder is resolved from `DB_MIGRATIONS_DIR` (set by the Dockerfile), so the bundled API
finds `packages/db/drizzle`.

## Production environment reference (API)

| Variable | Value |
| --- | --- |
| `NODE_ENV` | `production` |
| `API_HOST` | `0.0.0.0` |
| `PORT` | injected by Render (used when `API_PORT` is unset) |
| `TRUST_PROXY` | `true` |
| `REPOSITORY_DRIVER` | `postgres` |
| `DATABASE_URL` | Render internal connection string |
| `DB_AUTO_MIGRATE` | `true` (single instance) |
| `DB_MIGRATIONS_DIR` | `/app/packages/db/drizzle` (set in the image) |
| `STORAGE_LOCAL_DIR` | `/data/storage` (persistent disk) |
| `API_KEY` | shared secret; injected by the Worker |
| `CORS_ORIGIN` | `https://sheetpilot.com` (defense in depth; the SPA is same-origin) |
| `ALLOW_INSECURE` | leave unset. Production refuses to boot with the memory driver and/or no `API_KEY`. |

Optional: `MAX_UPLOAD_MB`, `RETENTION_UPLOAD_TTL_HOURS`, `AI_PROVIDER`/`OPENAI_API_KEY`/`AI_MODEL`
(see `.env.example`). Configuring a non-`noop` AI provider is a data-processing decision — event
descriptions leave the process.

## Verification checklist

- `npm run lint`, `npm run typecheck`, `npm test`, `npm run build` are green.
- CI runs the same, plus `npm audit --omit=dev --audit-level=high` and a Postgres job that applies
  migrations and runs the end-to-end smoke test against a real database.
- `GET /healthz` returns 200 (liveness) and `GET /readyz` returns 200 only when Postgres answers.
- Upload → configure → run → review → export completes and a report downloads through the Worker.

## Operations and limits

- **Single API instance.** No durable queue yet; runs are in-process and in-flight runs are marked
  failed after a restart (`recoverStaleRuns`).
- **Back up together:** the Postgres database and the `/data` disk (artifacts reference uploads by
  storage key).
- **Disk growth:** deliverables under `runs/` are never swept; unreferenced uploads are swept on the
  retention interval. Monitor the disk.
- **Logs:** structured JSON (`LOG_LEVEL=info`). `LOG_PRETTY=true` requires the `pino-pretty`
  devDependency and is not installed in the pruned production image.
- **Rollback:** Redeploy a previous Render deploy; for the Worker, `wrangler rollback` or redeploy a
  previous commit.

## Shared object storage (Cloudflare R2)

By default files live on a local disk (fine for one instance). To share files between the API and the
worker, or to run more than one API instance, use S3-compatible storage:

1. Create an R2 bucket and an S3 API token (Access Key ID + Secret).
2. Set on the API and worker services:
   - `STORAGE_DRIVER=s3`
   - `S3_BUCKET=<bucket>`
   - `S3_ENDPOINT=https://<accountid>.r2.cloudflarestorage.com`
   - `S3_REGION=auto`
   - `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY`
3. The Render persistent disk is then optional; remove it if you fully move to R2.

Objects are written under `uploads/…` and `runs/…`, so R2 lifecycle rules can expire them independently.

## Observability

- Every request carries an `x-request-id` (an inbound header is honoured, otherwise one is minted) and
  logs a structured completion line (`reqId`, method, url, statusCode, durationMs).
- `/healthz` is liveness; `/readyz` proves Postgres connectivity.
- Recommended: ship logs to Render's log stream, add a Sentry DSN for error tracking, and alert on 5xx
  rate, failed runs, queue depth and disk/R2 growth.

## Backups and disaster recovery

- **Postgres:** enable Render's automated backups + point-in-time recovery; record the RPO/RTO and run a
  restore drill at least once.
- **R2:** enable object versioning (or a bucket replication rule) so a bad delete is recoverable.
- **Together:** the database and the object store must be restored to the same point — run snapshots and
  artifacts reference each other by id/key.
- **Migrations:** forward-only, applied by the pre-deploy step or `DB_AUTO_MIGRATE=true` on a single
  instance. Never run migrations from more than one process at once.

```bash
npm ci
npm run build
docker compose up -d postgres
DATABASE_URL=postgres://sheetpilot:sheetpilot@localhost:5432/sheetpilot npm run db:migrate
NODE_ENV=production REPOSITORY_DRIVER=postgres \
  API_KEY=dev-secret API_HOST=127.0.0.1 \

  node apps/api/dist/index.js
```
